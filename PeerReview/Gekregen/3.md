### User story

**Pluspunten:**
- De wireframe bevat netjes annotaties.
- Er zijn subissues gelinkt en deze zijn uitgewerkt.
- Er is een branch gelinkt aan de story.
- De pull request bevat toelichting over de gerealiseerde functies.
- De commit messages komen overeen met de inhoud van de code.
- De acceptatiecriteria van de story en twee subissues zijn duidelijk en niet al te technisch.

**Minpunten:**
- De titel van de issue komt niet overeen met de titel van de story. 
- De story lijkt eerder een samenvoeging van twee stories (zoeken *en* filteren). Dit is ook te zien in het feit dat de subissues aparte acceptatiecriteria hebben. Het was misschien handiger geweest om de story op te splitsen.
- De Definition of Ready (DoR) is niet duidelijk aangegeven. Het is beter om deze bovenaan de user story te zetten, omdat hieraan voldaan moet zijn voordat eraan gewerkt mag worden.
- De annotaties voor de wireframe staan buiten de image. Er zijn Figma tools waarmee je de annotaties ook in de wireframe zelf kan hebben; dit leest iets duidelijker.
- Ik snap niet wat een 'testcase' is in de DoD. Ik zie geen Gherkin scenarios, frontend tests of manual test (of deze zijn niet gelinkt).
- In extra details i see "...Het component ontvangt een array van declaraties van de parent..." but there is no notes of what this array is or what it looks like.
	- Both sub-issues have this line: "Er wordt alleen gezocht binnen de lijst met declaraties die al in de lijst staan, dus wordt er niks nieuws verwacht van de backend". This lijst met declaraties should be annotated for clarity. Currently there is no lijst met declaraties described in the issue.
	- No domainmodel or erd present in the user story. No bpmn or other way to describe the business process. I get it that it seems to be a purely frontend user story but those things are still important.
- De PR is zonder commentaar door twee teamgenoten goedgekeurd. 
- De commit `add search and filter component that can be reused` introduceert ~1146 nieuwe regels aan code. Er zijn 13 LitComponents in een keer toegevoegd. Ik vind het zelf fijner om vaker te committen zodat ik een rollback kan uitvoeren indien ik iets volledig sloop oid.

### Frontend

**Max:**
- `styles.css` staat in de root-folder van `frontend`.

- Er staat ook een `.env`-bestand in de repo. In plaats van dit bestand toe te voegen aan `.gitignore`, zijn de variabelen hierin verwijderd.

- In `index.html` staat een `<style>`-tag in plaats van Lit te gebruiken. Ook staan er op regels 59–62 in deze `<style>`-tag lege headers.

- Regel 17 van `app.js` gebruikt `innerHTML`.

- In `app.js` is gebruikgemaakt van handmatige routing. Bij de huidige implementatie wordt elke pagina volledig opnieuw geladen elke keer als er geswitcht wordt.

- Er is rekening gehouden met een 404-pagina en die wordt correct aangeroepen.

- `rejection-reason.js` staat in de `src`-folder in plaats van in de `features`-folder.

- Er wordt veel gebruikgemaakt van `div`-elementen.

- Er zijn geen atoms voor headers, p-tags, buttons, etc., waardoor er per JS-bestand veel CSS nodig is. Dit is opvallend, omdat er wel bijvoorbeeld een `approval/complete-button.js` is.

- Er staan geen JSDoc-comments.

- In `claims-service.js` is correct gebruikgemaakt van `async/await`.

- In `claims-service.js` is er geen error handling.

- In `claims-service.js` staat bovenaan:

  ```JavaScript

  const API_BASE = '/api';

  ```

  Het is beter om dit bijvoorbeeld in de `.env` te zetten (bijv. `API_BASE`), zodat dit makkelijk en zonder fouten aangepast kan worden.

**Rijk:**

**Pluspunten:**
- Het `search-filter` component is goed granulair. 

**Minpunten:**
- De filestructuur van de frontend is niet erg overzichtelijk. `claim-rejection` (een feature?) staat in de root van `src` ipv. `features`, en er is ook nog een aparte `view` directory mey componenten.
- Op regels 35 en 38 van `date-field.js` wordt styling toegepast in de div elements zelf ipv. in de styles functie. Het leest prettiger om deze divs ids te geven en die te gebruiken als selectors.
- Er wordt weinig semantische HTML gebruikt en veel divs, bijvoorbeeld in `search-filter.js` (vanaf begin render functie op regel 128).
	- In de algemen frontend, op hoger niveau, wordt wel netjes gebruik gemaakt van semantische HTML.
- De styling van `claim-list.js` staat in een aparte file, `claim-page-styles.js`. Echter wordt `claim-page-styles` alleen binnen `claim-list` gebruikt. Dit is meer persoonlijke voorkeur (en ik snap het splitsen, omdat er ~140 regels aan styling zijn), maar het is makkelijker om snel de styling te zien indien deze in het component zelf staat.
