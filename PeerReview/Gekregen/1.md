# Frontend

## 1. Onderhoudbaarheid: Gebruik van Magic Strings
Het Probleem: Er worden hardcoded strings direct in de logica gebruikt.
Voorbeeld: `frontend/src/features/declaratie-details/components/claim-details.js` (Regel 24).

We zien hardcoded status-checks zoals `'APPROVED'`.

Waarom dit een probleem is:
Refactoring wordt foutgevoelig en tijdrovend. Bijvoorbeeld: het wijzigen van een status van `'APPROVED'` naar `'COMPLETED'` vereist een handmatige search and change :) actie door de hele codebase, wat het risico op bugs verhoogt.

Aanbeveling:
Extraheer deze waarden naar een gedeeld `constants.js` of `Enum` bestand. Verwijs in de hele applicatie naar deze constante in plaats van de string zelf.

---

## 2. Architectuur: Herbruikbaarheid van Componenten & Pagina-logica
Het Probleem: Code-duplicatie over meerdere dashboard-pagina's.
Betrokken bestanden:
* `frontend/src/pages/finance-dashboard-page.js`
* `frontend/src/pages/manager-dashboard-page.js`
* `frontend/src/pages/office-manager-dashboard-page.js`

**Observatie:**
Alle drie de pagina's delen exact dezelfde layout-structuur, maar zijn gedupliceerd om interne logica en API-calls individueel af te handelen.

```html
<app-header></app-header>
<dashboard-component
    .claims=${this.claims}
    .loading=${this.loading}
    .nextStatus=${this.nextStatus}
></dashboard-component>
```
Aanbeveling:

Momenteel heb je drie afzonderlijke dashboard-versies geïmplementeerd op basis van interne logica, maar een efficiëntere aanpak is het bouwen van één generic dashboard-component dat alle core functionaliteit en API-calls encapsuleert. Aangezien de primaire rol van een page slechts het populeren van componenten met specifieke context is (zoals de user identity of daadwerkelijke assets in plaats van placeholders), hoort de business logica niet op paginaniveau.

Ik adviseer om dit te refactoren naar één generieke component die door de drie specifieke pagina's wordt aangeroepen. De pages blijven hierdoor logic-free en dienen enkel om de context naar het component te injecteren. Dit waarborgt de modulariteit van je architectuur: mocht je in de toekomst extra componenten aan een pagina willen toevoegen, dan raakt je codebase niet vervuild met de logica van het dashboard.


---

## 3. Scheiding van Verantwoordelijkheden: Loskoppelen van Logica en UI Atoms
het Probleem: Low-level UI-componenten ("atoms") maken directe API-calls.
Voorbeeld: `frontend/src/shared/dashboard/components/atoms/complete-button.js` (Regel 41).

Gevonden code:
```js
await this.httpClaimService.updateClaim(this.claim);
```

Waarom dit een probleem is:
UI-componenten (zoals knoppen) moeten generiek zijn en niets weten van businesslogica. Door ze te koppelen aan een specifieke service, worden ze onmogelijk te hergebruiken in andere delen van de applicatie.

Aanbeveling:
Gebruik een generic button die een custom event (bijv. `@click`) verstuurt (emits). Handel de daadwerkelijke API-logica af in de bovenliggende container.


## 4. Consistentie: Naamgevingsconventies
 Het Probleem: Inconsistente schrijfwijze (casing) gebruikt voor rol-validatie.
 Bestand: `frontend/src/view/services/auth-service.js` (Regels 80 & 85).

Observatie:
* Regel 80: `user.role === 'office-manager'` (kebab-case, kleine letters)
* Regel 85: `user.role === 'Financieel'` (Met hoofdletter)

Aanbeveling:
Standaardiseer naamgevingsconventies (bij voorkeur kleine letters of `SCREAMING_SNAKE_CASE` constanten) door de hele applicatie heen. Dit voorkomt verwarring voor nieuwe ontwikkelaars en vermijdt eenvoudige casing-bugs.

## Extra

`/src/pages/finance-dashboard-page.js`

this line:
```js
this.claims = {...await claimsService.getClaimsByStatus('SECOND_APPROVED');}
```

is not best practice
We have recently run into feedback from Alex about how we should fetch data in the frontend. That if we fetch data this way, we're only getting the reference to an object, not the object itself. That can create issues with inconsistent data. If you wnat to make it best practice - make copies of the object, by encasing the fetching like this: `this.claims = {...await claimsService.getClaimsByStatus('SECOND_APPROVED');}`
