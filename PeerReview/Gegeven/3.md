# Peer review

## User story

### Minpunten - U.S

- De sprint is niet geselecteerd in het Project, alleen d.m.v een label
- De user story bevaat emojis dit is onprofessioneel.
- Er staat een design in die niet in de user story voorkomt.
- Notes/Additional info is erg vaag.
- Er is geen DoR
- In de DoD staat er dat er comments moeten zijn waar nodig, alleen in de code zijn geen comments. Dit is aangevinkt maar is niet zo.
- In de DoD staat er dat op zn minst 1 iemand een review geplaatst moet hebben. Dit is aangevinkt maar is niet zo.

### Pluspunten - U.S

- Er zijn goede gherkin scenarios.
- De user flow ziet er goed uit.
- De icons in de designs zijn gelinkt aan de fontawesome pagina
- Goede uitleg bij de wireframe
- PR/Branch gelinked aan de user story

## Pull request

### Minpunten - P.R

- Hij is door niemand gereviewed (behalve copilot) en hij is gemerged
- De Pull request is niet geassigned
- De beschrijving is erg karig
- Ook de namen van de commits zijn erg karig
- Niks gedaan met de feedback van copilot

### Pluspunten - P.R

- Het aantal commits is goed
- Copilot is gebruikt voor reviews

## Front-end

### Minpunten - F.E

- In de index.js regel 15 en app.js regel 15 zijn lines uitgecomment, of je laat ze staan en je gebruikt ze of je haalt ze weg.
- login-form.js regel 73 is een magic string
- Er wordt vooral veel html vertaald van Engels naar Nederlands, valt dit niet buiten de scope van de U.S?
- In de acceptatiecriteria wordt er gesproken over een approve of reject button die grijs moet worden als erop is gedrukt, maar dit is niet in de code gerealiseerd en wel aangevinkt in de criteria, hierdoor klopt de gherkin scenario ook niet meer.



### Pluspunten - F.E

- Goed gebruik gemaakt van een enum voor de status
- Console.log is er uit gehaald
- Styles in een aparte file
- De toast is altijd gerenderd in de html en word pas visible als er een nieuwe message is. Dit voorkomt extra complexiteit met het dynamisch toevoegen van nieuwe html.
